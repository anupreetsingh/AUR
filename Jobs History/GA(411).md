You should know:

For example, two processes could both access virtual address 0x400000, while those addresses map to completely different physical locations.

2. MMU address translation

Since you explicitly wrote "MMU address translation," I could ask:

What exactly does the MMU do?

You should be able to say something like:

The CPU generates a virtual address. The MMU translates that virtual address into a physical address using the process's page-table mappings. It first benefits from cached translations in the TLB; if the translation isn't cached, the hardware may perform a page-table walk.

You should understand that a virtual address conceptually contains:

Virtual Address
┌─────────────────────────┬──────────────┐
│ Virtual Page Number     │ Page Offset  │
└─────────────────────────┴──────────────┘

Translation changes the page portion:

Virtual Page Number ──page table──> Physical Frame Number

Physical Address
┌─────────────────────────┬──────────────┐
│ Physical Frame Number   │ Page Offset  │
└─────────────────────────┴──────────────┘

The offset doesn't change during translation.

3. Page tables

You should understand what a page-table entry contains conceptually:

Virtual page
    ↓
Page Table Entry
    ├── Physical frame number
    ├── Present/valid bit
    ├── Read/write permissions
    ├── User/kernel permissions
    ├── Accessed bit
    └── Dirty bit

You don't necessarily need to memorize the exact bit layout of x86-64 PTEs unless the assignment actually required it.

4. Multi-level page tables

This is probably the area I'd probe most because you explicitly mention it.

You should be able to explain why we don't just have one enormous page table.

For a simplified example:

Virtual Address

┌────────┬────────┬────────┬────────────┐
│ L1 idx │ L2 idx │ L3 idx │   offset   │
└────────┴────────┴────────┴────────────┘
    ↓        ↓        ↓
   table → table → table → physical frame

The address itself tells the MMU which entry to select at each level.

The major reason for multiple levels is memory efficiency: lower-level page tables only need to exist for portions of the virtual address space that are actually being used.

You should also understand the tradeoff: without a TLB, multi-level translation can require several memory accesses just to determine where the requested memory actually resides.

5. TLB

Even though your bullet doesn't explicitly say TLB, I'd definitely expect you to know it because it's tightly coupled to MMU translation.

TLB = Translation Lookaside Buffer.

It caches recent:

virtual page → physical frame

translations.

So instead of doing:

Virtual address
      ↓
L1 page table
      ↓
L2 page table
      ↓
L3 page table
      ↓
L4 page table
      ↓
Physical address

every time, the CPU can frequently get the translation directly from the TLB.

You should know the distinction between a TLB miss and a page fault. A TLB miss does not necessarily mean the page isn't in RAM; it can simply mean the translation isn't currently cached in the TLB.

6. Page faults

Because your résumé explicitly says "kernel page-fault handling," I'd expect you to explain what happens after a page fault.

A solid conceptual explanation is:

The CPU tries to access a virtual address. The MMU cannot complete the access based on the current page-table state, so the CPU traps into the kernel's page-fault handler. The kernel determines why the fault occurred and whether the access is valid.

And importantly, page fault does not automatically mean "load something from disk."

There are multiple reasons:

Page fault
   ↓
Kernel examines fault
   ↓
   ├── Valid but page not resident
   │       → bring/map page into memory
   │
   ├── Valid demand allocation
   │       → allocate physical page
   │
   ├── Copy-on-write
   │       → create writable copy
   │
   ├── Protection violation
   │       → access may be rejected
   │
   └── Invalid address
           → process may receive SIGSEGV

That's an important interview distinction.
