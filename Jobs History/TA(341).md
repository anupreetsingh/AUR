## Project 1 (Linked List)

### Problem Statement

Implement the `CentCom` and `Elevator` classes declared in `centcom.h`. `CentCom` represents a building's central elevator controller and owns a fixed-size dynamically allocated array of `Elevator` pointers. Each elevator represents its physical floors with a doubly linked list and maintains separate singly linked lists for upward and downward requests.

The implementation must create and retrieve elevators by ID, configure an inclusive range of floors, secure or unsecure floors, register valid button requests, process those requests in travel order, manage elevator load and emergency state, and release all dynamically allocated memory. An elevator cannot process a request while idle, overloaded beyond `LOADLIMIT`, or in an emergency. Its movement direction, door state, current floor, and request lists must remain consistent after every operation.

### Highlight of the Solution

- Initialize `CentCom` with a null-initialized dynamic array of elevator pointers. Treat a nonpositive array size or negative building ID as an empty controller.
- Use the elevator ID directly as an array index after checking `0 <= ID < m_numElevators`, and reject a floor range whose bottom is greater than its top. When installing an elevator at an occupied index, deallocate the previous elevator before replacing it.
- Represent the physical building range as an inclusive doubly linked list from `m_bottom` to `m_top`. Negative floor numbers naturally represent underground floors.
- Build the floor list from top to bottom because `insertFloor()` inserts only at the head and accepts only the floor immediately below the current bottom. Keep both `m_next` and `m_previous` links consistent.
- Keep `m_currentFloor` as a pointer into the physical floor list rather than storing a separate floor number. A newly configured elevator begins at its bottom floor.
- Store requests above the current floor in `m_upRequests` in ascending order and requests below it in `m_downRequests` in descending order. Reject nonexistent, secured, current-floor, and duplicate requests.
- When the first request is registered, change the movement state from `IDLE` to `UP` or `DOWN` and close the doors.
- Process the head of the active request list by following `m_next` or `m_previous` through the physical floor list, then remove and delete the processed request node. Continue in the same direction while requests remain, reverse when only the opposite list remains, or become idle and open the doors when both lists are empty.
- When a floor becomes secured, remove any pending request for that floor and update the direction, door, and idle state if the removal empties a request list.
- Make the emergency state sticky: `pushEmergency()` may set it to true but cannot clear it. Only `CentCom::clearEmergency()` clears an elevator's emergency state.
- Add entering load to `m_load`; subtract exiting load without allowing the total to become negative. A load greater than `LOADLIMIT` prevents request processing.
- Use small search and head-deletion helpers for repeated list operations. `clear()` must delete the physical floor list and both request lists, then restore the elevator's default state.
- In `CentCom`'s destructor, delete every owned elevator before deleting the pointer array. Each elevator destructor is responsible for deleting its own linked-list nodes.

### Notes

#### Linked List

A linked list stores data in dynamically allocated nodes. Instead of requiring adjacent memory like an array, each node contains data and one or more pointers that connect it to other nodes.

```text
Array:         [A][B][C][D]          Elements occupy adjacent memory.

Linked list:   [A|•] ──▶ [B|•] ──▶ [C|•] ──▶ [D|null]
                node       node       node       node
```

The first node is the **head** and the final node is the **tail**. An empty list is represented by a null head pointer.

- Accessing the head is $O(1)$.
- Searching for an arbitrary value is $O(n)$ because nodes must be followed sequentially.
- Inserting or deleting at a known position is $O(1)$ once the required node pointers are available.
- Dynamic allocation allows the list to grow one node at a time, but every allocated node must eventually be deleted.

#### Singly Linked List

A singly linked node points only to the next node. Traversal therefore moves in one direction.

```text
head
 │
 ▼
[2|•] ──▶ [5|•] ──▶ [8|•] ──▶ [12|null]
```

Project 1 uses singly linked lists for `m_upRequests` and `m_downRequests`. Request nodes need only `m_next` because each request list is processed from its head.

##### Inserting at the Head

Preserve the old head before replacing it. The new node must point to the old head, and then the head pointer can move to the new node.

```text
Before                         After inserting 1

head                           head
 │                              │
 ▼                              ▼
[2] ──▶ [5] ──▶ null           [1] ──▶ [2] ──▶ [5] ──▶ null

newNode->next = head
head = newNode
```

##### Deleting the Head

Save the old head, advance the list head, and then delete the removed node. Deleting first would lose the only safe path to the next node.

```text
Before                         After deleting 2

head                           head
 │                              │
 ▼                              ▼
[2] ──▶ [5] ──▶ [8]           [5] ──▶ [8]
 ▲
 old  ───────────────────────▶ delete old
```

##### Inserting in Sorted Order

Track both the current node and its predecessor. When the insertion position is found, connect the new node to `current` before connecting `previous` to the new node.

```text
Before                         After inserting 6

[2] ──▶ [5] ─────────▶ [8]    [2] ──▶ [5] ──▶ [6] ──▶ [8]
         ▲               ▲
      previous         current

newNode->next = current
previous->next = newNode
```

#### Doubly Linked List

A doubly linked node stores pointers to both the next and previous nodes. This requires more memory and pointer maintenance than a singly linked list, but it supports traversal in either direction.

```text
null ◀── [−2] ◀──▶ [−1] ◀──▶ [0] ◀──▶ [1] ◀──▶ [2] ──▶ null
          ▲                                          ▲
       m_bottom                                    m_top
```

Project 1 uses a doubly linked list for the elevator's physical floors. Moving upward follows `m_next`; moving downward follows `m_previous`. The endpoint invariants are:

- `m_bottom->m_previous == nullptr`
- `m_top->m_next == nullptr`
- For adjacent nodes `A` and `B`, `A->m_next == B` and `B->m_previous == A`

##### Inserting a New Bottom Floor

`insertFloor()` accepts only a floor whose number is exactly one less than the current bottom floor.

```text
Before                              After inserting floor −1

m_bottom                            m_bottom
   │                                   │
   ▼                                   ▼
  [0] ◀──▶ [1] ──▶ null              [−1] ◀──▶ [0] ◀──▶ [1] ──▶ null
                                          old bottom

newBottom->next = oldBottom
oldBottom->previous = newBottom
m_bottom = newBottom
```

#### The Three Lists in an Elevator

The physical floor list and request lists contain separate `Floor` objects. A request node records a requested floor number; `m_currentFloor` points to the corresponding node in the physical floor list.

```text
Physical floors (doubly linked)

m_bottom                                                     m_top
   │                                                           │
   ▼                                                           ▼
 [−2] ◀──▶ [−1] ◀──▶ [0] ◀──▶ [1] ◀──▶ [2] ◀──▶ ... ◀──▶ [12]
                              ▲
                         m_currentFloor = 1

Up requests (ascending)                 Down requests (descending)

m_upRequests                            m_downRequests
     │                                       │
     ▼                                       ▼
    [4] ──▶ [8] ──▶ [12] ──▶ null          [0] ──▶ [−2] ──▶ null
```

This ordering implements an elevator-style scan:

- While moving up, process the nearest higher request first and continue upward.
- When no upward requests remain, reverse only if downward requests exist.
- While moving down, process the nearest lower request first and continue downward.
- When both lists are empty, become `IDLE` and open the doors.

#### Elevator State Transitions

The linked lists determine what work exists, while the state variables determine whether and how the elevator may perform it.

```text
IDLE + OPEN
    │
    │ valid request above/below
    ▼
UP or DOWN + CLOSED
    │
    ├── process request; same-direction list remains ──▶ continue direction
    │
    ├── active list empty; opposite list remains ─────▶ reverse direction
    │
    └── both request lists empty ─────────────────────▶ IDLE + OPEN

Emergency active or load > 2000 lbs ─────────────────▶ request is not processed
```

#### Secured Floors

A secured physical floor remains in the building's floor list, but the elevator cannot accept or retain a request to stop there.

```text
Before securing floor 8              After securing floor 8

Up requests: [4] ──▶ [8] ──▶ [12]   Up requests: [4] ──────▶ [12]
                         │                            [8] is deleted
                         └── pending request

Physical floors: floor 8 remains present with m_secured = true.
```

#### Memory Ownership

Each owner must delete the objects it allocated. Request nodes are independent copies, so clearing a request list must not delete nodes from the physical floor list.

```text
CentCom
   │
   └── owns Elevator* array
          ├── Elevator 0 ── owns physical floors + up requests + down requests
          ├── Elevator 1 ── owns physical floors + up requests + down requests
          └── ...
```

Destruction proceeds from the inside out: each `Elevator` deletes all three lists, `CentCom` deletes each elevator, and then `CentCom` deletes the pointer array.

#### Operation Complexity

| Operation | Time | Reason |
| --- | ---: | --- |
| Get an elevator by valid ID | $O(1)$ | Direct array indexing |
| Insert a new bottom floor | $O(1)$ | Head insertion |
| Find a floor | $O(n)$ | Sequential traversal |
| Register a request | $O(n)$ | Search and sorted insertion |
| Process the next request | $O(n)$ | Move through physical floor nodes |
| Clear an elevator | $O(F + U + D)$ | Delete every physical, up-request, and down-request node |

## Project 2 (Trees)

### Problem Statement

Implement the `Fleet` class declared in `fleet.h`. A fleet stores dynamically allocated `Ship` objects, uniquely ordered by ship ID, and can be configured as a binary search tree (BST), AVL tree, Splay tree, or `NONE`.

The implementation must support insertion, removal, tree-type conversion, clearing, destruction, and deep-copy assignment while preserving the required tree properties and node heights. Valid ship IDs range from `MINID` through `MAXID`; invalid and duplicate IDs are ignored. AVL trees must rebalance after insertions and removals, while a newly inserted Splay-tree node must be moved to the root. Removal is not performed on Splay trees.

### Highlight of the Solution

- Initialize every fleet with a null root and its requested tree type; use postorder traversal in `clear()` and the destructor to safely deallocate every node.
- Reject insertion when the type is `NONE`, the ship ID is outside the permitted range, or the ID already exists.
- Perform ordinary BST insertion recursively, updating each ancestor's height while the recursion unwinds.
- Maintain AVL balance with a balance-factor helper and left/right rotation helpers. Handle right-right and left-left imbalances with single rotations and right-left and left-right imbalances with double rotations.
- After a Splay-tree insertion, recursively identify the zig-zig or zig-zag case and rotate the inserted ship to the root.
- Remove BST and AVL nodes using the standard leaf, one-child, and two-child cases. For two children, copy the in-order successor's data and recursively remove the successor so heights and AVL balance are repaired along the path.
- Convert a populated BST or Splay tree to an AVL tree by traversing the old tree in postorder, detaching and resetting each node, and reinserting it into a fresh balanced tree. Setting the type to `NONE` clears the fleet.
- Implement assignment with a self-assignment check, cleanup of the destination, copying of the tree type, and a recursive deep copy so the two fleets do not share nodes.
- Keep leaf height at `0` by treating a null child's height as `-1`, and update rotation heights from child to parent.

### Notes(Extension of original .Pages Notes)

#### Binary Tree

Each node has at most two children.

#### Binary Search Tree (BST)

A derivative of binary tree where each node contains a key and a value pair. The key determines the position of the node in the tree, and the value is the data to be stored.

- If the target key is less than the key at the current node, traverse to the left child.
- If the target key is greater than the key at the current node, traverse to the right child.
- If the keys are equal, the action is determined by our application of the tree. More on this later.

Worst case - Our BST can become a linked list where each of the new keys is greater or smaller than the previous one inserted.

Best Case- It forms a complete tree.

Search: **Log n** time complexity

#### AVL Tree

AVL employs rotations during insertion or deletions to balance a BST. In this, the height difference between the left and right subtrees of any node(**Balance factor**) must be at most 1.

$$
bf = h_l - h_r
$$

So only possible value for $bf$ are going to be -1, 0, 1 in a balanced scenario, otherwise the tree is unbalanced.

Whenever the absolute value of $bf$ for a node turns out to be 2. We do Rotations. Types of rotations depends case by case on the structure causing the imbalance.

#### Cases of Imbalance

1. **RR Case:** RR signifies that the imbalance at node A is due to it being **right heavy** (with $bf = -2$, so it requires balancing) and the right child of A(B in this case) also being right heavy (with $bf = -1$, not to the point of requiring balancing).

   **Left Rotation:** So we do a left rotation on A, which involves:

   - making A left child of B
   - making left child of B the new right child of A.
   - Whatever was pointing to A now points to B

   ```text
   Before                         After left rotation on A

       A                                      B
        \                                    / \
         B                 ───────▶         A   C
          \
           C
   ```

2. **LLCase:** LL signifies that the imbalance at node A is due to it being **left heavy** (with $bf = 2$, so it requires balancing) and the left child of A(B in this case) also being left heavy (with $bf = 1$, not to the point of requiring balancing).

   **Right Rotation:** So we do a right rotation on A, which involves:

   - making A right child of B
   - making right child of B the new left child of A.
   - Whatever was pointing to A now points to B

   ```text
   Before                         After right rotation on A

           A                                  B
          /                                  / \
         B                 ───────▶         C   A
        /
       C
   ```

3. **LRCase:** LR signifies that the imbalance at node A is due to it being left heavy(with $bf = 2$, so it requires balancing) and the left child of A(B in this case) being right heavy (with $bf = -1$, not to the point of requiring balancing).

   **Double Left-Right Rotation:**

   - Left Rotation on B
   - Right Rotation on A

   ```text
   Before                 Left rotation on B         Right rotation on A

         A                        A                            C
        /                        /                            / \
       B          ───────▶      C            ───────▶        B   A
        \                      /
         C                    B
   ```

4. **RL Case:** RL signifies that the imbalance at node A is due to it being right heavy(with $bf = -2$, so it requires balancing) and the left child of A(B in this case) being left heavy (with $bf = 1$, not to the point of requiring balancing).

   **Double Left-Right Rotation:**

   - Right Rotation on B
   - Left Rotation on A

   ```text
   Before                 Right rotation on B        Left rotation on A

       A                        A                              C
        \                        \                            / \
         B          ───────▶      C          ───────▶        A   B
        /                          \
       C                            B
   ```

Search: **Log n** time complexity. But insertions and deletions are more expensive compared to BSTs due to need for rotations to maintain the balance factor.

#### Splay Tree

In this splaying operation is performed which means after an operation(search, insertion, deletion, etc) the tree is restructured by performing tree rotations so that the accessed node becomes the root node.

Search: Amortized average time complexity is **Log n** over a sequence of operations. It adapts to access patterns where frequently accessed nodes are moved closer to the root making future access faster.

## Project 3 (Heap)

### Problem Statement

Implement the `SQueue` class declared in `squeue.h`. The queue stores dynamically allocated social-media `Post` objects and returns posts according to a configurable priority function rather than their insertion order. An `SQueue` can operate as either a min-heap or max-heap and can use either a skew-heap or leftist-heap structure.

The implementation must support insertion, removal of the highest-priority post, merging compatible queues, clearing, reporting the queue size, traversal-based printing, deep-copy construction, and deep-copy assignment. Changing the priority function, heap type, or structure must rebuild the existing heap while preserving all posts. A merge between queues with different configurations must throw a `domain_error`, and removing from an empty queue must throw an `out_of_range` exception.

### Highlight of the Solution

- Store the heap root, number of posts, priority-function pointer, heap type, and structure type as the complete state of an `SQueue`.
- Centralize heap behavior in a recursive `merge` helper. Select the higher-priority root according to the priority function and whether the queue is a min-heap or max-heap, then recursively merge the other heap into its right subtree.
- For a skew heap, swap the root's children after every recursive merge. This keeps the tree self-adjusting without maintaining explicit balance information.
- For a leftist heap, swap children only when the left child's null path length is smaller than the right child's, then set the node's NPL from its right child.
- Insert a post by making an independent one-node heap and merging it with the existing heap. Reject a post when its priority function returns `0`.
- Remove the next post by copying the root, merging its left and right subheaps, deleting the old root, decrementing the size, and returning the saved post.
- Merge compatible queues by transferring the right-hand queue's nodes into the current queue; update the combined size and leave the right-hand queue empty. Treat self-merge as a no-op.
- Rebuild after a priority-function, heap-type, or structure change by traversing the old heap in postorder, detaching each node, resetting its NPL, and merging it into a fresh heap without allocating replacement nodes.
- Implement the copy constructor and assignment operator as deep copies that preserve the exact heap shape, post data, NPL values, priority function, heap type, and structure. Guard assignment against self-assignment.
- Clear memory with a recursive postorder traversal, reset the size to zero, and use the same operation from the destructor.

### Notes(Extension of original .Pages Notes)

#### Heap

An implementation of a priority queue ADT(Abstract Data Type), where elements are arranged and accessed based on their priority(and not order of insertion or such). Usually a complete binary Tree that follows the Heap Property.

##### Heap Property

- **Min Heap:** Parent value < Left and Right Child value. In this case we mean to say that lesser value means a higher priority. So, the function that calculates that priority value is designed differently.
- **Max Heap:** Parent value > Left and Right Child value. In this case we mean to say that greater value means a higher priority. So, the function that calculates that priority value is designed differently.

```text
Min Heap                               Max Heap
(smaller value = higher priority)      (greater value = higher priority)

          1                                      9
        /   \                                  /   \
       3     2                                7     8
      / \   /                                / \   /
     7   5 6                                3   4 6
```

#### Complete Binary Tree

Meaning all levels are fully filled except possibly the last one which is filled from left to right. Heap are many times complete.

```text
             1
           /   \
          2     3       Every level is full except the last,
         / \   /        which is populated from left to right.
        4   5 6
```

#### Skew Heap

Root node has max priority.

```text
         9        The root has the highest priority.
       /   \      No complete-tree shape is required.
      4     7
       \   /
        2 6
```

#### Leftist Heap

A skew heap but every node store a Null Path Length(NPL). NPL is the minimum number of edges from the node to a descendant node that has a null child(i.e. fewer than 2 children).

During merge if the NPL of a right child is greater than NPL of left child, we swap the children essentially making left subtree heavier than the right subtree.

```text
Before child swap                    After child swap

       A                                    A[1]
     /   \                                 /    \
  B[0]   C[1]             ───────▶      C[1]   B[0]
         / \                           / \
      D[0] E[0]                      D[0] E[0]

Right NPL > Left NPL                 Left NPL >= Right NPL
```

## Project 4 (Hash Table)

### Problem Statement

Implement the `DnaDb` class declared in `dnadb.h`. The database stores dynamically allocated `DNA` records in an open-addressed hash table. Each record is uniquely identified by the combination of its DNA sequence and location ID, while the supplied hash function hashes the sequence. Valid location IDs range from `MINLOCID` through `MAXLOCID`, and the table capacity must be a prime within `MINPRIME` and `MAXPRIME`.

The database must support insertion, lazy removal, lookup, location-ID updates, and deferred changes among linear, quadratic, and double-hash probing. When the current table's load factor exceeds `0.5` or its deleted ratio exceeds `0.8`, the database must begin incremental rehashing into a new table. During this process, lookups and removals may involve both tables, insertions go only to the current table, and each subsequent insertion or removal transfers approximately 25% of the old table.

### Highlight of the Solution

- Normalize the requested capacity to the next prime within the permitted range, allocate a null-initialized pointer array, and initialize all current-table, old-table, probing-policy, counter, and transfer-index state.
- Centralize collision handling in a probing helper. Use $(h+i)\bmod N$ for linear probing, $(h+i^2)\bmod N$ for quadratic probing, and $((h\bmod N)+i(11-(h\bmod 11)))\bmod N$ for double hashing.
- Probe past lazily deleted records during lookup so a tombstone does not hide a matching record later in the probe sequence. During insertion, remember or reuse a deleted bucket while still rejecting duplicates found in either table.
- Insert only valid, unique records into the current table, store them with `m_used = true`, and update the current size or deleted counter depending on whether the destination was empty or a tombstone.
- Search both the current and old tables while rehashing. Return a default `DNA` object when no live match exists.
- Remove a record lazily by setting `m_used = false` and incrementing the deleted counter for the table that contains it. Do not break its probe chain by immediately freeing the bucket.
- Update a location ID only when the target exists, the new ID is valid, and the resulting sequence/location pair is unique. The record can remain in its bucket because the hash function uses only the sequence.
- Compute the current-table load factor as `m_currentSize / m_currentCap` and the deleted ratio as `m_currNumDeleted / m_currentSize`.
- Start rehashing when $\lambda > 0.5$ or the deleted ratio is greater than $0.8$. Move the current table into the old-table fields, create a new prime-capacity table sized from the number of live records, and activate the most recently requested probing policy.
- Advance the transfer index through roughly one quarter of the old table after each insertion or removal. Copy live records into the current table, mark their old copies deleted, and deallocate the old table once every old entry is accounted for.
- Treat `changeProbPolicy()` as a deferred request: store the new policy immediately but apply it only when the next rehash creates a new current table.
- In the destructor, delete every allocated `DNA` record in both tables and then delete both pointer arrays.

### Notes(Extension of original .Pages Notes)

#### Hash Tables

Hash Table is a data structure that allows us to implement map ADT.

It works by taking a key, running it through a hash function to get an index, and using that index to store the value in an array-like structure. Here's the core idea:

**Hash function:** Converts the key (e.g., a string) into an integer (the hash), which is then mapped to an index in the underlying array.

**Collision handling:** Since multiple keys might hash to the same index, techniques like chaining (storing a list at each index) or open addressing (probing for the next available slot) are used to handle collisions.

👉 In many Programming language Dictionaries are implemented using Hash Tables under the hood.

**Average time complexity:**

- Lookup: O(1)
- Insert: O(1)
- Delete: O(1)

#### Probing In Hash Table

We use a Hash function on Each Key to determine an Index number of an array cell(bucket).

A Hash function takes a key and returns an index,

$$
Index = Hash(Key) \bmod Table\_size
$$

The value of hash could be any great value, we bring it in the $0$ to $Table\_size - 1$ range by taking modulo(%) with $Table\_size$. But by doing so, we raise the probability that many Hash values can lead to the same index. And If different keys result in result in the same index, that is called a collision.

When we get the same Index for more than one key value, the hash table uses a collision Handling policy scheme for storing the new value. Some example of such policies could be:

1. **Linear Probing**

   In linear probing, if the computed index is already occupied, the algorithm checks the next slot (i.e., moves one step forward) until an empty bucket is found.

   This is simple to implement but can lead to primary clustering, where groups of consecutive occupied slots make future collisions more likely.

2. **Quadratic Probing**

   To reduce clustering, quadratic probing uses a non-linear jump pattern. Instead of checking the next bucket, it checks buckets at increasing square intervals. This helps spread the keys out more evenly.

3. **Double Hash Probing**

   Double hashing uses a second hash function to determine the step size for probing. It offers the best distribution and minimizes clustering by varying the probe step based on the key itself.

```text
Example: table size = 11 and the key's initial index = 4

Linear probing       4 ──▶ 5 ──▶ 6  ──▶ 7       (+1 each time)
Quadratic probing    4 ──▶ 5 ──▶ 8  ──▶ 2       (+0², +1², +2², +3²) mod 11
Double hashing       4 ──▶ 7 ──▶ 10 ──▶ 2       (second hash gives step size 3)
```

#### Rehashing In Hash Table

Rehashing in a hash table is a process to resize the table and redistribute the keys when certain conditions are met.

##### When Rehashing typically occurs?

- The load factor exceeds a threshold(commonly 0.75)

  $$
  Load\ Factor = \frac{number\ of\ elements}{size\ of\ Table}
  $$

- There are two many Collisions
- Sometimes, when deletions cause the table to become too sparse

##### Why does Rehashing Occur?

- Reduce Collisions to improve performance
- Maintain O(1) time complexity

##### How does Rehashing Occur?

- Creates a new table that is typically 2X larger than the current table
- Recalculate the hash for each key using the new table size
- Insert each key into the new table using the new hash values

```text
Old table                                  New, larger table

[A][·][B][C][·][D][·]       ───────▶       [·][C][·][·][A][·][·][D][·][B][·][·][·]
                                              ▲           ▲        ▲     ▲
                                      Keys receive new indices because the capacity changed.
```

#### Incremental Rehashing

In incremental rehashing, instead of rehashing the entire table at once, the system rehashes small chunks of data gradually over several operation(insertion, deletion, lookup)

##### Why not do full Rehashing?

- To avoid performance dips, rehashing the entire table at once can take O(n) time, if that happens during a user-facing operation, the app might freeze or lag briefly.
- Systems like web servers, games, or databases can’t afford long pauses.

```text
Start         Old [PPPP][PPPP][PPPP][PPPP]    New [    ]
Operation 1   Old [MMMM][PPPP][PPPP][PPPP]    New [25% ]
Operation 2   Old [MMMM][MMMM][PPPP][PPPP]    New [50% ]
Operation 3   Old [MMMM][MMMM][MMMM][PPPP]    New [75% ]
Operation 4   Old [MMMM][MMMM][MMMM][MMMM]    New [100%]  ──▶ delete old table

P = pending range    M = scanned/migrated range
```

#### Lazy Deletion

Lazy deletion means that an object isn’t actually removed from memory when it’s deleted. Instead its status is just marked as deleted(for Project 4, m_used=False) and the entry is left in the table.

##### Why use Lazy Deletion?

- Lazy deletion avoids the need to resize or rehash the table immediately when an item is deleted, which can be expensive in terms of performance.
- We can just get rid of the deleted items when we rehash the table.
- Till then if the collision with deleted items is disabled, we can insert new items in their place.

```text
Before removal                      After lazy removal

[i] ──▶ DNA { m_used = true }       [i] ──▶ DNA { m_used = false }
                                                ▲
                                                └── tombstone remains in the probe sequence

Lookup:     continues probing beyond the tombstone.
Insertion:  may reuse the tombstone's bucket.
Rehashing:  discards the tombstone instead of transferring it.
```
